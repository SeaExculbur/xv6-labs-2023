# 操作系统笔记 · 系统调用与 Unix 抽象

> 课程背景：xv6 教学操作系统（RISC-V 架构）

## 一、操作系统的目标

几乎所有操作系统都有一些共同的目标：

- **硬件抽象（abstraction）**：操作系统是硬件的抽象层，在一堆硬件之上提供更高层次的接口和抽象，让上层软件不必直接面对硬件细节。
- **多路复用（multiplexing）**：让多个应用程序共享硬件资源，例如 CPU 在多个进程之间轮转执行、内存被多个程序划分使用。
- **隔离性（isolation）**：与线程隔离的思想类似——一个应用程序挂了，不应该导致与其不相干的程序挂掉，也不应该导致整个系统崩溃。
- **共享性（sharing）**：用户之间可以在系统里相互分享需要的文件和信息。
- **安全 / 权限（security/permission）**：访问控制系统，用于管理谁被允许访问什么内容、以什么方式访问、是否有权限修改。
- **高性能（performance）**：让硬件性能发挥到极致。
- **支持多种用途（range of uses）**：同一个操作系统必须能支持各种不同的应用场景，如数据库等。

## 二、计算机的分层结构

一个可使用的计算机可以抽象成**三层**：

- **上层**：软件（应用程序）
- **中层**：系统内核
- **底层**：硬件

内核通常内置了很多服务与数据结构，例如：

- **文件系统 FS**：把磁盘上的数据映射成操作系统能看懂的文件树，并且让上层程序与底层硬件解耦——程序不用关心在不同硬件上如何找扇区、如何定位和读写数据，这些都由 FS 代劳。即：程序 → 内核中的 FS → 磁盘。
- 除了 FS，内核还提供**进程管理、内存分配、访问控制（安全相关）、网络通信**等服务。

## 三、系统调用（system call）

系统调用是程序与内核之间的接口（API → 内核）。

### 3.1 系统调用看起来像普通的函数调用

程序要打开一个文件时，可以调用名为 `open` 的系统调用，把文件名作为参数传给它：

```c
fd = open("file1", 1);
```

这个调用实际上会进入内核代码执行：内核检索这些参数，执行 `open` 的内核实现（可能访问磁盘），然后返回一个值给 `fd`，这个 `fd` 就是**文件描述符（file descriptor）**。程序之后可以通过文件描述符来访问这个已打开的文件。

写文件同理：调用 `write`，传入文件描述符：

```c
write(fd, "hello\n", 6);
```

意思是：把这些字符放入内存，让操作系统把该内存地址的 6 个字节写入文件描述符 `fd` 对应的文件。

进程创建也是类似的形式：

```c
pid = fork();
```

### 3.2 系统调用与普通函数调用的区别

系统调用最终会**跳转到内核**，这是它与普通程序函数调用的本质区别。

编译器如何处理系统调用？生成的汇编代码是否是对某个代码段的过程调用？

答：RISC-V 中有一条特殊指令。执行 C 程序中的系统调用（如 `open`、`write`）时，从技术上讲 `open` 是一个 C 函数，但该函数内部的指令实际上是机器指令——也就是说我们调用的 `open` 并不单纯是一个 C 函数，它实际上是由汇编程序实现的。在 RISC-V 中，这条特殊指令叫做 **`ecall`**：它把控制权转移给内核，内核随后查看进程的内存和寄存器，确定相关参数。

**注意——缓冲区溢出风险**：如果要求读取的字节数（`read` 的第三个参数）比缓冲区实际大小要大，操作系统会把所有字节都复制到提供的内存地址内——也就是写到缓冲区之外，覆盖栈上其他位置的内容。所以调用 `read` 时，n 不能超过缓冲区实际大小。

### 3.4 示例程序：open.c

<img src="C:\Users\123\AppData\Roaming\Typora\typora-user-images\image-20260825204631392.png" alt="image-20260825204631392" style="zoom:50%;" />

（截图：`open.c` 源码。以 `O_WRONLY | O_CREATE` 打开/创建 `output.txt`，写入 `"ooo\n"` 共 4 字节。）

调用 `open` 函数时，程序会进入内核执行内核里的 open 实现，并使用 `O_` 开头的**标志位（flags）**来指定打开方式：`O_WRONLY` 表示只写，`O_CREATE` 表示文件不存在则创建，多个标志用按位或（`|`）组合。然后写入 `"ooo\n"`，一共 4 个字节。open 返回一个文件描述符 fd，之后把相同的文件描述符与缓冲区一起传给 write；对于文件描述符所索引的文件，有多种写入数据的方式。

**文件描述符的本质**：fd 实际上是索引到内核内的一个小表——内核为每个正在运行的程序（进程）维护一张表，记录该进程的每个文件描述符分别指向什么。

**每个进程都有自己的文件描述符空间**：两个不同的进程各自打开文件时，可能拿到相同的文件描述符编号，但内核为每个进程维护单独的文件描述符表，所以即使编号相同，在不同进程中也可能对应不同的文件。

### 3.5 shell 与重定向

shell 集合了多个工具，可以用它完成一些操作，比如 `ls`，并且可以对输入输出重新定向：

- `ls > out`：ls 的所有输出被送入 out 文件；
- `grep x < out`：从 out 文件里取出包含 x 的输出。

`<` 与 `>` 有点像 C++ 的输入输出流重定向。

## 四、fork 系统调用

以简单的 fork 为例：fork 会拷贝当前进程的内存，并创建一个新的进程，于是计算机里就有了两个内存内容相同的进程。

fork 系统调用在**两个进程中都返回**，但返回值不同：

- 在**原始进程（父进程）**中，fork 返回一个大于 0 的整数 pid——这是**新创建的子进程**的 pid；
- 在**新进程（子进程）**中，fork 返回 0。

所以即便两个进程内存相同，依然可以通过 fork 的返回值区分它们——用返回值打破旧进程与新进程的对称性。

<img src="C:\Users\123\AppData\Roaming\Typora\typora-user-images\image-20260825211841820.png" alt="image-20260825211841820" style="zoom:50%;" />

（截图：`fork.c` 源码。调用 fork 后打印返回值，`pid == 0` 打印 "child"，否则打印 "parent"。）

**问题：fork 返回的子进程，总是与父进程相同，还是也可能不同？**

在 XV6 中，除了 fork 的返回值不同，其余都是相同的（指令、数据、栈等）。两个进程各有一份副本，位于各自独立的内存地址中；它们都认为自己的地址空间从 0 开始（栈在顶部、向下增长），但实际是不同的内存。在更复杂的操作系统中会有一些不同的细节，可能导致父进程与子进程不同，但在 XV6 中是一样的。除了内存相同，**文件描述符表也会被复制**：如果父进程打开了一些文件，子进程也会看到一组相同的文件描述符（子进程看到的是复制的文件描述符表）。

另外，每次运行 shell 命令时，shell 都会 fork 一个进程来运行该命令（比如 `ls`），但还需要某种方法让这个新进程去执行 `ls` 的指令——这就是 exec 系统调用的作用。

## 五、exec 系统调用：用新程序替换当前进程

### 5.1 exec 的语义

exec 系统调用从指定的文件中读取指令，并替换调用它的进程：从该文件加载指令，覆盖掉当前进程的内存映像，丢弃当前内存，然后开始执行这些新指令。

### 5.2 示例程序：exec.c

<img src="C:\Users\123\AppData\Roaming\Typora\typora-user-images\image-20260826184052063.png" alt="image-20260826184052063" style="zoom:50%;" />

（截图：`exec.c` 源码。第 12 行调用 `exec("echo", argv)`。）

第 12 行执行了 exec 系统调用，它的作用是执行 echo 里的指令，并允许接收一串命令行参数。实例里传入了一个以空指针结尾的字符串指针数组：

```c
char *argv[] = { "echo", "this", "is", "echo", 0 };
exec("echo", argv);
```

该数组相当于运行 echo 命令并传入三个参数：this、is、echo（argv[0] 是程序名本身，不算参数）。

**数组结尾的 0 是什么**：例子中的 `0` 是一个空指针，放在数组最后一个位置，标记数组内容的结束——双引号内的每个字符串实际上是指向某块内存的指针，该内存包含了这些字节；数组的最后一个元素是一个值为 0 的指针，也就是所谓的空指针。内核中的 exec 实现会**遍历**这个数组，直到找到值为 0 的元素为止。（注意：这个 0 是告诉内核参数到哪结束，不是"告诉编译器"。）

**整个执行过程**：首先 exec.c 进程产生，开始执行里面的程序；碰到 exec 系统调用后进入内核，内核使用传入的参数和命令执行相关操作——把 exec.c 进程的内存替换成 echo 程序的内存映像（进程本身还是同一个，进程号不变）。

### 5.3 exec 的特点

- **成功后不返回**：exec 完全替换了当前进程的内存，原始 exec 调用自然不会返回结果。exec 返回的唯一情况就是内核里发生了一些错误，导致 OS 无法为用户运行该程序——比如程序不存在，exec 返回 -1。
- **保留文件描述符表**：exec 会保留当前进程的文件描述符表，不管 exec 之前引用的文件描述符是 0、1、2 还是其他，新程序里也会引用相同的东西。

### 5.4 为什么 shell 用 fork + exec 而不是直接 exec

以上例子展示的是程序如何用文件里的另一个程序替换自己。但在 shell 里，我们执行命令（比如 `ls`）时**不希望 shell 自己被替换**——shell 不能直接在自己的进程里调用 exec，否则执行完 `ls` shell 就没了。因此 shell 实际做的是：**先 fork 出一个子进程，再让子进程 exec**。这是 Unix 的惯用范式（fork + exec idiom）。

## 六、fork + exec + wait：shell 运行命令的完整流程

### 6.1 示例程序：forkexec.c

<img src="C:\Users\123\AppData\Roaming\Typora\typora-user-images\image-20260826200022111.png" alt="image-20260826200022111" style="zoom:50%;" />

（截图：`forkexec.c` 源码。第 12 行 fork，子进程分支 exec echo，父进程分支 wait。）

```c
int pid, status;
pid = fork();                        // 第 12 行
if(pid == 0){                        // 子进程
    char *argv[] = { "echo", "THIS", "IS", "ECHO", 0 };
    exec("echo", argv);
    printf("exec failed!\n");        // 第 16 行：exec 失败才会执行到这里
    exit(1);                         // 第 17 行
} else {                             // 父进程
    printf("parent waiting\n");
    wait(&status);                   // 第 20 行
    printf("the child exited with status %d\n", status);
}
exit(0);
```

流程：父进程 fork 出子进程 → 子进程 exec 变成 echo 并执行 → 父进程 wait 阻塞等待子进程退出 → 子进程退出后父进程继续打印其退出状态。这就是"**如果想要运行一个程序，但又要拿回控制权，就 fork，再让子进程 exec**"。

### 6.2 wait：等待子进程退出

如果第 12 行的 fork 返回了大于 0 的数（父进程），就调用 wait 系统调用，**等待子进程退出**。这相当于同步阻塞——父进程在 wait 处停住，直到子进程结束。和 socket 服务端阻塞等待客户端消息、然后继续循环是相似的思路。

在输出提示符（让用户输入下一条命令）之前，shell 必须等命令结束，所以 wait 就用于等待它的**任何一个**子进程返回。

### 6.3 exit 与退出状态

退出状态（status）是子进程把执行结果传递给父进程的一种方法：

- 子进程调用 `exit(1)` 时，会把一个 32 位整数值从退出的子进程传递给等待的父进程（第 17 行）；
- 操作系统会把这个值从退出的子进程传递给父进程的 wait（第 20 行）——内核向 wait 传入的地址（`&status`）写入 exit 中的参数；
- Unix 惯例：**退出码 0 表示成功，非 0（如 1）表示出错**。

正常情况下，子进程 exec 成功，第 16、17 行根本不会执行；只有 exec 失败才会走到 `exit(1)`。如果关心子进程是否成功，父进程可以查看 wait 拿到的 status 来确定。

### 6.4 课堂问答

**问 1：既然 exec 系统调用在成功之前不会返回值，那么第 12、13 行的代码是否还会执行？**

答：经过实操运行，这个程序实际上运行了 echo 里的指令，进程的 fork 与替换都成功执行，没有报错信息——即第 16、17 行的代码没有被执行。只有在出现错误时，exec 才会返回（返回 -1），控制权才会回到 exec 之后的代码。

**问 2：为什么父进程在子进程 exec 完成之前就已经完成了输出？**

答：exec 系统调用开销很大，因为它必须加载所有指令：访问文件系统，把名为 echo 的文件内容从磁盘读入内存，分配内存，再释放旧进程的内存——所以 exec 中有很多机器指令，需要足够长的时间。因此在 exec 完成、开始运行 echo 之前，父进程就已经完成了它的输出。另外，在 xv6 中父进程等待子进程只能通过 wait 这一种机制。

**问 3：当我们说"子进程复制了父进程的所有内存"，具体指什么？**

答：编译一个 C 语言程序后，程序会变成内存里的一些指令，它们只是内存中的一些字节，可以被复制到其他地方。xv6 中 fork 的做法是：复制父进程的虚拟内存映射（页表），并把父进程的物理内存内容复制一份给子进程，使子进程和父进程的内存映射看起来一样、内容相同，但位于各自独立的内存中。

**问 4：如果一个父进程有多个子进程，wait 在第一个子进程返回后就返回，这是否意味着父进程需要多种方法来保证所有子进程都完成？**

答：是。如果一个进程 fork 了两次，就需要调用两次 wait。每次 wait 返回时，它都会返回被回收的那个子进程的进程 id（pid），父进程据此区分到底是谁退出了。

## 七、IO 重定向的实现：fork + close + open + exec

### 7.1 问题引入

系统调用是如何结合在一起实现 IO 重定向的？例如 `echo hello > out` 这类命令。

### 7.2 示例程序：redirect.c

<img src="C:\Users\123\AppData\Roaming\Typora\typora-user-images\image-20260827163415488.png" alt="image-20260827163415488" style="zoom:50%;" />

（截图：`redirect.c` 源码——先 fork，在子进程里 close(1)、open("output.txt")，再 exec echo，把输出重定向到文件。）

```c
// redirect.c: run a command with output redirected
int main()
{
    int pid;

    pid = fork();
    if(pid == 0){
        close(1);
        open("output.txt", O_WRONLY|O_CREATE);

        char *argv[] = { "echo", "this", "is", "redirected", "echo", 0 };
        exec("echo", argv);
        printf("exec failed!\n");
        exit(1);
    } else {
        wait((int *) 0);
    }
    exit(0);
}
```

### 7.3 实现原理

shell 先运行 fork，然后在**子进程**里修改文件描述符的设置方式，让子进程的文件描述符 1 指向新文件。按照惯例，大多数程序使用 fd 1 作为输出（标准输出），之后执行的命令就输出到重定向目标。

**为什么先 close(1)**：我们不想要父进程的 fd 1——也就是 shell 连接到控制台的描述符，所以先把它关闭，只在子进程中进行 IO 重定向。

**为什么 open 一定返回 1**：open 的语义是返回当前进程**最低的未使用**文件描述符号。close(1) 之后，1 正好是最低未使用的编号，所以 open 必然返回 1，把文件描述符 1 连接到这个文件。如果子进程不先 close(1)，open 就不会返回 1（0、1、2 都已被占用时，它会返回 3 之类的编号），重定向就会失效——echo 的输出仍会写到原来的控制台。

open 调用以后，文件描述符 1 连接到了这个文件；接着执行 echo，echo 会输出到描述符 1，内容就写入了这个文件。**echo 不知道自己被重定向了**——它只知道自己输出给了描述符 1；但 shell 知道。

同时，父进程（shell 自己）的 fd 1 没有被改变，仍然连接到控制台。**在子进程中改变文件描述符，是 fork 的惯用用法**：重定向了运行命令的输入和输出，而不影响调用程序（shell 本身）的输入和输出。

### 7.4 fork 与 exec 分离的意义

这个例子展示了 fork 和 exec 之间的巧妙分离。fork 和 exec 是**两个独立的系统调用、独立函数**：

- fork 返回后、exec 执行前的这段时间里，子进程运行的仍然是调用进程的指令（代码的副本）；
- 所以调用进程仍然能够改变事情、仍然处于控制中——**即使 fork 和 exec 之间有间隔，调用进程的指令仍然在执行**；
- 正是这个间隔给了 shell 机会去更改文件描述符所引用的内容（先 close 再 open），然后才走到 exec。

### 7.5 小结：哪一步决定了重定向

**决定性的一步是 open 系统调用**（在 close(1) 之后执行，恰好返回 1，把 fd 1 指向文件）；exec 不是决定者，只是"受益人"。

- **exec 不改变文件描述符表**：它替换的是代码和内存，fd 表原样保留。所以 echo 运行时看到的 fd 表，就是 exec 之前调好的那张表——它写 fd 1，内容就进了文件。
- **为什么必须在子进程里做**：fd 表是每个进程私有的副本，子进程改自己的 fd 表，父进程（shell）完全不受影响——shell 自己的 fd 1 仍然连着控制台，等子进程结束后还要继续和用户交互。
- **open 内部的动作顺序**：找到最低空闲编号 → 把 fd 表表项指向新打开的文件对象 → 返回编号。所以 fd 表的修改发生在返回之前，open 返回 1 的那一刻，重定向已经完成。
- **用词注意**：是"文件描述符表"（fd table），不是"文件描述符页"——"页"是内存页（page）的概念，不要混。
- **心智模型**：fork（复制 fd 表）→ close(1)（腾出编号）→ open（表项指向文件，重定向完成）→ exec（echo 用这张表）。
- **迁移预告**：管道（pipe）也是同样的思路——fd 表项指向内存中的管道对象。改程序看到的"编号指向什么"，就能改程序的行为。

## 八、本课总结

本节课讲了 Unix：它有许多接口，核心是 **Unix 的 IO 抽象和进程抽象**。这些接口相对简单——只是传递一个整数（文件描述符、进程 id），把它作为系统调用的参数传递。这与 Unix/Linux"一切皆文件"的思想相符。
