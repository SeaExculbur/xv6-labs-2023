# xv6 Lab1 primes 题：踩坑与知识点总结

> 题目：并发素数筛——用 pipe + fork 搭流水线，第一个进程喂入 2~35，每个素数对应一个进程，过滤自己的倍数后传给下一个进程。思路出自 Doug McIlroy（Unix 管道发明者）。

## 0. 这道题真正在考什么

**"函数递归传参"和"进程间传数据"是两回事**——这是本次踩的最大坑，也是 primes 和 pingpong 的分界线：

- fork 后父子进程**内存隔离**：父进程变量的改动子进程看不见，反之亦然
- 进程间传数据的**唯一通道是管道**（字节流）
- 管道 = 进程间的"函数参数"：一个进程"收到输入"的方式不是 C 参数，而是从管道 read 出字节

所以不能写一个"过滤数组 → 递归传数组"的函数，那只是单进程思维。primes 的正确模型：

```
main 进程：写 2..35 进管道1 → 关写端 → 自己变身第 1 关
    ↓ 管道1
第 1 关（进程）：read 第一个数=2 → 打印 → 建管道2 + fork 子进程 → 过滤 2 的倍数写管道2
    ↓ 管道2                    （子进程变成第 2 关，递归执行同样逻辑）
第 2 关（进程）：read 第一个数=3 → 打印 → 建管道3 + fork ...
    ↓ 管道3
    ... 链式直到 EOF
```

**为什么第一个读到的数一定是素数**：它到达第 n 关意味着没被前面所有素数（2,3,5…）整除——这是数学保证，不是巧合。

## 1. 本次代码的错误清单（对照自查）

第一版代码把进程模型写成了函数模型，逐条错误：

| # | 代码 | 错误 | 正确 |
|---|------|------|------|
| 1 | `int arr[35];` 直接使用 | **从未初始化**，2~35 没写进去，全是垃圾 | 先循环填充或直接从管道喂 |
| 2 | `fork_pipe(arr[35], 35)` | `arr[35]` 是**越界元素**（下标 0~34），不是数组名 | 传 `arr` |
| 3 | `pipe(p)` 写在 `fork()` **之后** | **致命**：fork 后两个进程各自执行 pipe，各建一根**互不相通的管道**——父写自己的、子读自己的，谁也读不到谁 | **pipe 永远在 fork 前** |
| 4 | `write(p[1], next_arr[35], 35)` | 越界元素当缓冲地址；写死 35 字节 | `write(p[1], next_arr, index * 4)`（index 个 int）|
| 5 | `read(p[0], res[35], 35)` | 同理越界 | `read(p[0], res, ...)` |
| 6 | 子进程递归 `fork_pipe(arr, index)` | 用的是**父进程 fork 前的旧 arr 副本**，管道读到的数据根本没被使用 | 子进程的数据来自**新管道的 read**，不是父进程变量 |

**共性教训**：fork 之后，任何"在子进程里读父进程变量"的写法都是错的——父进程变量的值在 fork 那刻就冻结了，之后两边各改各的。

## 2. 正确的关卡函数结构（primes 的全部逻辑）

```c
void sieve(int left_fd) {
    int p;
    if(read(left_fd, &p, 4) <= 0)   // ① EOF：没有输入 → 本关不存在
        return;
    printf("prime %d\n", p);        // ② 第一个数必为素数（grader 匹配格式！）

    int right[2];
    pipe(right);                    // ③ 右管道（给下一关）——fork 前！
    int pid = fork();
    if(pid == 0){
        close(right[1]);            // 子进程（下一关）只用右读端
        close(left_fd);             // 左管道是父进程的输入，子进程用不到
        sieve(right[0]);            // 递归当新关卡
        exit(0);
    }
    close(right[0]);                // 父进程（本关）只用右写端
    int prime = p;
    while(read(left_fd, &p, 4) > 0){      // ④ 循环读到 EOF
        if(p % prime != 0)                //    滤掉本关素数的倍数
            write(right[1], &p, 4);
    }
    close(right[1]);                // ⑤ 关键：关写端 → 下游 read 才能等到 0
    wait(0);                        // ⑥ 等子进程（整条链干净退出）
    exit(0);
}

int main() {
    int p[2];
    pipe(p);
    for(int i = 2; i <= 35; i++)
        write(p[1], &i, 4);
    close(p[1]);                    // 喂完关写端 = 给第 1 关发 EOF 信号
    sieve(p[0]);
    exit(0);
}
```

盯住三件事：**pipe 全在 fork 前**；**每进程只留"左读端 + 右写端"**；**EOF 靠关写端传播**。

## 3. read 与 EOF 的语义（本次两个追问的沉淀）

### 3.1 read 返回 = min(请求, 可用)，不是"管道总量"

```c
read(fd, buf, 4)    // 管道有 136 字节 → 返回 4（取走 1 个 int），剩 132
read(fd, buf, 400)  // 管道有 136 字节 → 返回 136（min(400, 136)，一次读光）
```

返回值是**字节数**（4 = 1 个 int），不是个数。sieve 每次只请求 4 字节 = 一次处理一个数字，循环直到 EOF——不是一次把管道读空。

### 3.2 为什么 while(read > 0) 不会死循环

管道**不是自己产生内容的**——数据是上游 write 进去的，有限。read 的完整语义：

| 情况 | read 行为 |
|------|----------|
| 管道有数据 | 返回 min(请求, 可用)（>0）|
| 管道空 + 还有写端开着 | **阻塞睡**（可能还有数据来）|
| 管道空 + 所有写端已关 | 返回 0（EOF：永远不会再有数据）|

**EOF 的开关握在写端手里**：上游写完 → close 写端 → 下游把剩余数据读完后，再 read 返回 0 → while 退出。EOF 沿链逐级传播（第 n 关关右写端 → 第 n+1 关等到 0）。

### 3.3 死锁的真相 = 没关写端

管道里还握着一个活写端 → 内核认为"数据可能还会来" → 下游 read 在空管道上**永远睡**。这就是为什么每级必须 close 多余端：xv6 每个进程只有 16 个 fd，进程数也有限，不关会资源耗尽 + 死锁。

## 5. 一句话心智模型

**primes = 一条进程流水线，管道是级间传送带，EOF 是上游关写端发的"下班铃"，每级只留"左读端 + 右写端"，第一个读到的数就是本级要筛的素数。**
